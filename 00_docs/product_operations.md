# 本番運用

現在の環境と有効な保存経路は [現行環境](../docs/current-state.md)、DB の契約は [Database](../docs/database.md)、ブラウザでの受入は [システムテスト](../docs/system-test.md) を参照する。

## 承認と実行前の確認

- 本番操作は対象 Issue に目的、対象環境、操作範囲、担当、停止条件、検証と切り戻し方法を記録し、明示の承認を受ける。アプリ配信は Vercel の配信管理者、DB の操作は対象 Supabase プロジェクトの DB 管理者が担当する。確認に使うのは承認済みの試験アカウントと検証用レコードとする。
- 配信管理者は Vercel プロジェクトと Production Branch、現在の本番ドメイン・配信 ID、対象ビルド・commit、保存経路を Vercel 側で照合する。GitHub の既定ブランチ、Vercel の Production Branch、現在ドメインに割り当てられたデプロイはそれぞれ確認する。
- DB 管理者は対象プロジェクト、適用済み migration、書込モード、承認済みの復旧点と復旧担当を照合する。schema・RLS・Auth の変更は明示された対象に限定し、schema は Git 管理の migration として検証する。新規 DB 用の [baseline migration](../supabase/migrations/20260902090014_current_app_baseline.sql) は既存本番 DB に実行しない。
- 秘密情報、実データ、復旧用の書き出しは承認された Git 管理外の場所に保全する。Issue には判断・結果とアクセス可能な参照先を記録し、秘密情報や健康記録の本文を貼らない。
- 対象、権限、現行の配信・書込状態、必要な復旧候補のいずれかを確認できない場合は、対象の操作を止める。

## 書込の凍結と再開

書込の制御点は `migration_private.daily_record_write_mode` の singleton 行。正規化の保存・削除 RPC は `normalized` を要求する。`frozen` はアプリからの正規化書込を拒否し、進行中の書込 transaction が終わるまでモード変更が待機し得る。読込やすべての管理者操作を止める設定としては使わない。詳細は [モードとロックの定義](../supabase/migrations/20261106033054_atomic_cutover_mirror.sql) と [現行 RPC](../supabase/migrations/20261125212008_retire_jsonb_runtime.sql) を参照する。

1. 保守枠と実行手順の承認を確認する。DB 管理者は現在値を `normalized` と照合し、その値を条件に singleton 行を `frozen` へ更新する。更新件数が1件であることと、確定後の読み戻しが `frozen` であることを確認する。ロック待ち、エラー、件数不一致、想定外の値があれば切替の続行を止める。
2. 承認済みの検証用レコードで、正規化の保存・削除が拒否され、データが変わらず、認証・読込・履歴が利用できることを確認する。検証中に実データを変更しない。
3. DB と配信の健全性、照合結果、書込再開の承認を確認する。DB 管理者は現在値 `frozen` を条件に singleton 行を `normalized` へ更新する。更新件数1件と確定後の値を確認する。
4. 検証用レコードで認証、保存・再読込、更新、履歴、削除と所有者境界を確認する。合格後に保守を解除する。不合格の場合は作業を止め、承認済みの停止条件に従って必要な書込停止を行い、確認結果と再開条件を記録する。

## アプリ切り戻しと DB 異常

- **アプリの障害**で DB の健全性が確認できる場合、配信管理者は現在の正規化 DB・Auth・書込モードと互換性を確認した既存ビルドを対象にする。候補の配信 ID、環境、保存経路、現行 API との互換、対象ドメインと受入結果を記録して承認を受ける。Vercel の rollback candidate 表示は配信上の候補を示すため、DB 互換性は別に確認する。 [Vercel の Instant Rollback](https://vercel.com/docs/instant-rollback)
- **既存ビルドを戻す**場合はビルド済み成果物の設定で動く。**旧 commit を再ビルドする**場合は、その世代が要求するビルド設定と依存を照合し、現在の正規化 DB に対応する `VITE_DAILY_RECORD_PERSISTENCE=normalized` の候補を隔離環境で検証してから承認に出す。必要な設定を確認できない候補は保留する。
- **DB の異常**や照合不一致がある場合は配信の切り戻しによる復旧を続けず、DB 管理者が保全・影響範囲・再開条件を確定する。書込モードが安全に確認できる場合は、承認済みの凍結手順に従う。旧 JSONB 経路への復旧は退役済み。
- 復旧後は本番ドメインと配信 ID、DB モード、承認済みの検証用レコードによる認証・読込・履歴と、書込再開時の CRUD を確認する。外部接続なしの凍結・原子性検証は [テスト方針](../docs/testing.md#normalized-database-verification) を参照する。
